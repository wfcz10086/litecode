# 动漫 MV / 配音短片

> ⭐ **固定流程, 别绕路**: 一切交给 `anime_short.py` (它会自动找「能力接入」里的生图 / H3 / AniSora / 配音 / 识别卡,
> 并行生成、逐镜头用识图模型审阅、失败换引擎、到点超时报错)。**别自己写轮询脚本**, 也别手工一个个调服务。

```bash
AS="python3 ${LITECODE_HOME:-/opt/litecode}/skills/anime-short/scripts/anime_short.py"
$AS check            # 先看服务: image(Qwen-Image) / h3 / anisora / tts(IndexTTS) / asr(SenseVoice), 至少要 image + 一个视频
```

## 用户通常只说一句话 —— 缺的自己补, 不要反问

| 用户没说的 | 自己这样定 |
|---|---|
| 用哪首歌 | 本对话里**最近生成 / 上传的歌** (`/tmp/litecode_workspace/music/` 或 uploads 里最新的那首, 结合上下文判断); 都没有就先用 ai-song 写一首 |
| 歌词 | 那首歌对应的 `*_歌词.txt` / lyrics.txt; 用户上传的歌没有歌词就只用识别结果做字幕 |
| 人物照片 | 这条或前几条消息里带的 `[file: …png/jpg]` 是人像 → 直接当 `ref_image`, 外貌照着照片写进 `character` |
| 画风 | 默认真人写实; 说了动漫 / 二次元才动漫 |
| 时长 | 整首歌 |
| 输出目录 | `/tmp/litecode_workspace/mv/<歌名>` (已存在且做过别的画风就加 `_写实` / `_动漫` 后缀, 不覆盖) |
| 真人肖像 | 用户给的真人照片: 回复里提醒一句"发布前确认本人同意", 不要因此停下 |
| 等不等 | MV 要几十分钟: **启动后报预计时间就结束本轮**, 用户问"好了吗 / 进度"时看日志汇报; 做完的成片下次对话交付 |
| "停掉 / 取消 XX" | 只停那个 MV 的进程 (`pkill -f "[m]v/<歌名>"`), 别动别的 |

例: 用户贴了张照片说"给这首歌做个 MV" → 歌 = 刚做的那首, ref_image = 这张照片, look = real, 时长 = 整首, 直接开干。

## 两种模式

| 模式 | 用户说法 | 做法 |
|---|---|---|
| **mv** | "做个 MV / 把这首歌做成 MV / 类似 XX 那种 MV" | 写歌 (或用用户给的歌) → 切成约 5 秒一段 → 每段: 首帧 + 这段音乐喂给 H3「参考生视频」, 画面跟着节奏动 → 拼接 → 换回完整原曲 → 歌词字幕 |
| **story** | "做个有对白的动画 / 动漫短片 / 配音动画" | 每个镜头: 首帧 → 图生视频 → 角色台词用 IndexTTS 配音 (可带情绪) 盖在 H3 环境音上 → 台词字幕 (+ 可选配乐) |

## 流程

1. **定画风开关 `look`**: **默认 `"real"` (真人写实)**; 只有用户明确说"动漫 / 二次元 / 国漫 / 卡通"才用 `"anime"`。
   **一条片子只用一种, 前后不能混**。real 只用 H3 (AniSora 只会动漫); 审阅也按这个标准查 (写实片里出现动漫画面算不合格)。
2. **定方案** (不要反问, 按常理补全): 主题、情绪走向、时长、画风、主角外貌。
   - **MV 时长默认 = 整首歌** (用户给了歌 / 要给某首歌做 MV 时, 不要自己截短); 只有用户说"预览 / 短一点 / 40 秒"才截。
     耗时参考: 每 5 秒一段, 有人唱的段走 H3 (每段 1.5~2.5 分钟), 纯伴奏段分给 AniSora 并行; 2 分钟的歌约 30~45 分钟, 开跑前告诉用户。
   - 剧情短片默认 4~6 个镜头。
   用户拿某首歌 / 某位歌手举例时, 只学**风格和情绪**: 歌词一律原创, 不照抄原词; prompt 里不写真实歌手名, 不模仿某人嗓音
   (把嗓音特点写成描述: 查 ai-song 技能里的「唱法风格参考表」, 刘欢 / 萨顶顶 / 可楼 / 韩红 / 腾格尔 等都有现成写法)。
3. **MV 先听歌, 做"歌词 → 时间点 → 场景 → 画面"映射** (歌已经有了就直接听; 没有就先用 ai-song 写好再听):
   ```bash
   $AS listen "$OUT/song.mp3" --lyrics "$OUT/lyrics.txt"
   ```
   输出每 5 秒一段的时间点、有没有人唱、唱的是哪句原词。照这张表在回复里先列一张映射表
   (段 | 时间 | 强弱 | 唱词 | 场景 | 画面), 再写 shots: 唱歌词的段 → 写 `lyric`; 纯伴奏 / 喊麦开场 → `kind: intro/instrumental/outro`。
   - **强弱**是每段响度的相对高低: 强 → 大动作、快推拉、冲击感 (副歌 / 高潮放最抓眼的镜头); 弱 → 舒缓、慢镜头、氛围。
     生成时脚本会按强弱自动给动作提示加料, 写 `motion` 时顺着它写。
   - **先确认再生成**: 用户说"先给我看看 / 确认后再做 / 先出方案"时, 列完映射表就停, 等用户回复再跑生成; 没这么说就一口气做完。
4. **写 plan.json** 存到 `$OUT/plan.json` (`OUT=/tmp/litecode_workspace/mv/<标题>`):
   ```json
   {
     "title": "从头来过",
     "look": "real",
     "resolution": "480p",
     "style": "日系动漫电影画风, 赛璐璐上色, 电影感光影, 竖版构图",
     "character": "三十多岁的中国男人, 短黑发, 胡茬, 深灰工装夹克, 眼神坚毅",
     "ref_image": "(可选) 用户给的人物照片路径 —— 写了就直接当定妆照, MV 里的人就是照片里的人",
     "song": {"prompt": "励志摇滚抒情, 主歌低沉压抑, 副歌激昂爆发, 浑厚有力的成熟男声, 电吉他, 弦乐, 鼓, 76 BPM",
              "lyrics": "[verse]\n…\n[chorus]\n…", "duration": 40},
     "shots": [
       {"image": "深夜空荡的厂房, 男人独自坐在台阶上, 冷色调", "motion": "镜头缓慢推近", "kind": "intro"},
       {"image": "雨夜街头, 男人蹲在路边看着积水里的倒影", "motion": "雨滴落下", "lyric": "风把灯吹熄的时候 路还认得我"},
       {"image": "清晨, 男人推开铁门走出去, 逆光", "motion": "他抬头迎着光迈步", "lyric": "把碎掉的自己拾起来 挺直腰 往前走"},
       {"image": "山顶日出, 男人张开双臂", "motion": "镜头环绕拉远", "kind": "outro"}
     ]
   }
   ```
   - MV 镜头**按唱词对齐**: 每个镜头写 `lyric` (它演的是哪句歌词, 原文照抄) 或 `kind` (`intro` 前奏 / `instrumental` 间奏 /
     `outro` 尾奏, 给没人唱的段落)。脚本拿到歌后先逐段听, **这段实际唱哪句就放演那句的镜头**, 纯伴奏段放 intro/instrumental/outro
     镜头; 副歌重复时会复用同一个镜头。前奏 / 间奏 / 尾奏镜头各准备 1~2 个 (空镜、氛围、人物特写), 歌词镜头覆盖每段主要唱词。
     结果里 `shot_map` 是 "第几段 → 第几个镜头"。不写 lyric / kind 就按顺序排 (不推荐)。
   - 情绪曲线和歌一致 (例: 低沉 → 爆发)。
   - **歌词行数按时长和速度算** (慢歌每句约 4 秒, 中快 3 秒, 留 6 秒前奏/尾奏; 40 秒慢歌 ≈ 8 句)。写完歌脚本会逐段听一遍:
     前奏 > 8 秒或歌词唱到不足 6 成就自动带要求重写一次 (结果在 RESULT 的 `song_qa`); 字幕只出现在真有人声的段落, 显示原歌词。
   - 歌词写法同 ai-song: [verse]/[chorus]/[bridge] 分段, 每行 6~12 字; 40 秒约 10~14 行。
   - story 模式不写 `song`, 每个 shot 加 `"lines": [{"who": "林晓", "text": "…", "emotion": "低落"}]`,
     顶层加 `"voices": {"林晓": "voice_03", "旁白": "voice_01"}` (音色 voice_01~voice_09); 要配乐加 `"bgm": {"prompt": "温暖钢琴", "volume": 0.15}`。
   - `resolution`: 默认 `480p` (竖版 480×864, 10 步); 只有用户明确说 720p / 高清才写 `720p` (768×1344, 约 2.3 倍耗时)。
   - 每个 shot 可写 `mode` 选 H3 视频模式 (不写: MV 用 r2v, 剧情用 i2v):

     | mode | 做什么 | 用在 |
     |---|---|---|
     | `r2v` | 参考生视频: 首帧当参考图 + 这一段音乐当参考音频, 画面跟节奏 | MV 主力 |
     | `i2v` | 图生视频: 从首帧动起来 | 剧情镜头 |
     | `fl2v` | 首尾帧: 从本镜头首帧过渡到 `last` 指定的画面: `"next"` = 下一个镜头首帧; 镜头序号; 或直接写一段画面描述 (脚本按定妆照画出尾帧)。写了 `last` 不写 mode 也按 fl2v | 转场, 让前后镜头连起来 (副歌前、场景切换) |
     | `t2v` | 文生视频: 只按文字生成, 不用首帧 | 没有主角的空镜 (天空、城市、风景) |

     一条 MV 里可以混用, 例: 主歌 r2v → 副歌前一段 fl2v 转场 → 副歌 r2v → 结尾 t2v 空镜。
   - `engine` 可选 `h3` / `anisora`, 不写就两边轮流 (并行, 快一倍); MV 带音乐参考的段落只能 H3。
5. **跑** (后台, 约 每段 3~5 分钟, 两路并行):
   ```bash
   $AS mv "$OUT/plan.json" -o "$OUT"          # 或 story
   ```
   用 execute_shell 的 background=true 跑, 期间看 `$OUT` 下 frames/ clips/ 的进度; 中断了**重跑同一条命令**会跳过做好的部分。
6. **交付**: 最后一行 `RESULT {...}`: `file` 成片、`srt` 字幕、`engines` 每段用了哪个引擎、`warnings` 审阅不合格 / 兜底的段落。
   回复里写成片路径 (网页出播放卡片)、歌词全文、每段用了什么、耗时; `warnings` 原样告诉用户, 别藏。

## 防错机制 (脚本自动做, 不用手工)
- **任务锁**: 同一输出目录同时只能跑一个任务, 重复启动直接报错 (不会两个任务抢同一台 H3)。要停任务: 会话和进程都停。
- **用户给了人物照片** ("做一个和这个人匹配的 MV"): plan 写 `"ref_image": "/tmp/litecode_workspace/uploads/xxx.png"`, 照片直接当定妆照;
  `character` 照着照片写清外貌 (发型/发饰/衣服/颜色), 想最像本人用 `"look": "real"`, 动漫化用 `"anime"`。
  照片是真人时, 提醒用户确认本人同意使用其肖像。
- **定妆照**: 有 `character` 时先画一张主角定妆照 (正面半身、纯色背景), **有主角出场的镜头**以定妆照为参考图来画, 人物长相/发型/服装保持一致;
  没有主角的镜头 (物件特写、空镜) 不套定妆照 —— 画面描述里没写人物会自动识别, 也可以在 shot 里写 `"cast": false`。
  参考图模式画风跑偏时第二次自动改用文生图 (人物外貌写进提示词)。
- **整体一致性比对**: 全部首帧画完后, 定妆照 + 所有首帧一起给识图模型看, 人物或画风不一致的镜头自动重画。
- **重试**: 网络抖动/超时同一服务先重试 1 次, 再换引擎, 再不行用首帧慢推镜头顶上 (写进 warnings)。
- **成片自查**: MV 成片时长必须和歌对齐 (误差 ≤ 1 帧, `av_drift_s`), 必须有音轨, 字幕条数够, 再抽 4 帧看画风/人物/字幕。结果在 RESULT 的 `self_check`。

## 标准流程里的自动环节 (脚本做, 不用手工)
歌词 → 时间点 (listen) → 场景/画面 (plan) → **提示词优化** (大模型把每个画面改写成生图/视频模型画得对的具体提示词:
抽象概念换成具体视觉、去掉画面里的文字和界面、保留原描述的主体动作表情、动作按唱词和节奏强弱写) → 生成 → 审阅 →
**不合格时大模型按审阅意见重写提示词再生成** → 成片自查。优化结果缓存在 `$OUT/prompts.json`。

## 出片后自修 (脚本自动做一轮)
出片后脚本会**逐段检查** (每段中间帧 vs 该段要求: 画面不符 / 画风不统一 / 乱码字 / 人物倒挂变形 / 动作跑偏),
有问题就让大模型按问题重写那个镜头的提示词、只重做它, 再重新合成 —— 自动一轮, RESULT 的 warnings 里写着修了哪些。
用户说"有几段不对 / 帮我修一下 / 再检查一遍"时, 对已有成片跑 (同一输出目录, 后台):
```bash
$AS repair "$OUT/plan.json" -o "$OUT"
```
用户点名某段 ("第 9 段的火箭不对"): 先在 plan.json 改那个镜头的 image / motion, 再跑 repair。

## 出片后自己修 (LiteCode 做, 不要等用户指出)
1. 看 RESULT 的 `warnings` / `self_check`, 再抽几帧用 vision_ocr 看一眼成片。
2. 有问题的镜头: 改 plan.json 里那个 shot 的 `image` / `motion` (写得更具体, 或换一个画得出来的画面), 删掉它的
   `frames/NN.png` 和用到它的 `clips/MM.mp4`、`clips/nMM.mp4` 以及 `final.mp4`, **重跑同一条命令** —— 做好的部分全部复用, 只重做这几个。
3. 回复里说清楚: 自查发现了什么、改了哪几个镜头、改后结果。

## 审阅 (自动)
- 每张首帧: 识图模型 (设置里的识图模型, 如 Qwen3.6) 检查是否符合画面要求、人物外貌、有无畸形 / 乱码字; 不合格带着问题重画一次。
- 每段视频: 抽 3 帧检查人物有没有崩、前后是不是同一个人; 不合格换另一个引擎重做; 都不行就用首帧慢推镜头顶上并写进 warnings。

## 出错
- `check` 里 image 或视频全是 ✗ → 告诉用户去「🔌 能力接入」接 Qwen-Image / MiniMax H3 / AniSora, 别硬做。
- `ERROR: …` 原样告诉用户是哪一步、什么错; 不要换成别的方式偷偷交差。
