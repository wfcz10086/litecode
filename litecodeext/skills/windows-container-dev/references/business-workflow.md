# 中文订单报价、Word 修改与复制审阅验收

由 LiteCode 在 Web 会话中编写业务代码并实际执行；本规范只定义输入、预期结果和证据。按短关卡推进，不重复安装已有环境。

## 范围与准备

- 仅新机：SSH `win-devtest`、桌面 `win-desktop-test`，先核对主机 `WIN-EXAMPLE01`。Windows GUI 每次明确传 `alias`，不使用控制端 Linux 的 `desktop_*`。
- 本轮生成唯一 `run_id`，专用目录 `C:\litecode-business\<run_id>`，对应 WSL `/mnt/c/litecode-business/<run_id>`；新建带本轮标记的独立容器，复用已验证的小镜像缓存。先检查端口，优先使用空闲 `8081`；占用时另选并记录，不抢占进程，不使用现有 `8080`。
- 保留现有 VS Code、开发容器和项目，不重启 Windows/WSL，不改变安全设置，不执行全局容器或镜像清理。
- GUI 文档阶段先检查已有 Word 或 LibreOffice Writer。缺失时，LiteCode 按用户已授权的依赖安装范围安装免费 Writer，复用可信缓存或校验官方安装包，同时继续业务代码开发，不重复请求确认。下载/安装失败才报告实际缺口并标记 GUI 待补验。核对真实产品/版本、窗口及 `.docx` 文件名；使用 Writer 验收时如实报告，不冒称使用了 Word，商业 Word 缺少授权时其专属兼容性仍为未测。记事本仅可作为 `review.txt` 的粘贴目标，不能代替文档应用。
- `ctrl+h`、`ctrl+p` 当前不在快捷键白名单。依据新截图使用菜单、`ctrl+f`、鼠标选择和已有快捷键，不编写键盘脚本绕过工具。

## 最小业务契约

实现订单 JSON 输入、报价 API 和可在 Windows 浏览器访问的网页。API 建议 `POST /api/quote`；页面实际提交同一数据并展示行金额、小计、折扣额、运费、税额及应付。接口和网页必须使用同一套业务计算，返回金额为两位小数的字符串。

固定主样例：

```json
{
  "order_id": "LC-BIZ-001",
  "customer": "青禾实验室",
  "delivery_date": "2026-11-06",
  "discount_rate": "0.075",
  "shipping": "12.30",
  "tax_rate": "0.06",
  "items": [
    {"name": "桌面支架", "quantity": 2, "unit_price": "129.90"},
    {"name": "连接线", "quantity": 5, "unit_price": "19.99"},
    {"name": "标签套装", "quantity": 3, "unit_price": "8.75"}
  ]
}
```

规则：从字符串构造 `Decimal`，禁止先转浮点数；金额每步用 `ROUND_HALF_UP` 保留两位。行金额=数量×单价，小计=行金额之和，折扣额=小计×折扣率，计税基数=小计−折扣额+运费，税额=计税基数×税率，应付=计税基数+税额。单价/运费为非负普通十进制字符串、最多两位小数；比率为 0～1 的十进制字符串、最多四位小数；拒绝 NaN/Infinity、指数形式和非字符串金额。数量必须为 1～9999 的整数，布尔值不算整数；订单行不为空，客户名不为空，日期为有效的 `YYYY-MM-DD`。校验失败返回明确的 4xx 与字段错误，不覆盖已生成文档。

独立核算的主样例预期：行金额 `259.80 / 99.95 / 26.25`，小计 `386.00`，折扣 `28.95`，运费 `12.30`，计税基数 `369.35`，税额 `22.16`，应付 **`391.51`**。半分舍入样例：数量 2、单价 `0.05`、折扣 `0`、运费 `0.00`、税率 `0.05`，税额应为 **`0.01`**，应付 **`0.11`**。

## 文档与复制对象

生成小型 `quote-original.docx`：含客户、订单号、明细表和全部金额，另含以下单独一段；将 `<run_id>` 替换为本轮真实标记：

> 审阅摘录｜订单：LC-BIZ-001｜客户：青禾实验室｜交付日期：2026-11-06｜含税应付：391.51元｜标记：<run_id>

保留原件及哈希，复制成 `quote-reviewed.docx` 后在 Word/Writer 中修改：**只把该段交付日期改为 `2026-11-09`，金额和标记保持不变**。日期仅在该审阅段出现，避免遗漏另一处。GUI 保存后禁止通过脚本重写这份修改稿。

先准备本轮独立 `review.txt` 的空白编辑窗口。随后在 Word/Writer 中真实选中修改后的整段，`ctrl+c`，用 `clipboard` 读取并核对实际完整文字；切换该目标窗口，`ctrl+v` 并保存。`type_text` 默认通过剪贴板输入，会覆盖已有剪贴板；复制到真实粘贴之间不要调用它，也不要用脚本或重输原文冒充粘贴。保存对话框中的路径可在粘贴后输入。先确认焦点与空白目标，避免覆盖其它文件或用户草稿。

## 九个短关卡

| 关卡 | 实际操作与通过标准 |
|---|---|
| 1. 主报价 | API 提交主样例并记录 HTTP 状态/完整 JSON；Windows 浏览器在业务端口实际提交并显示 `391.51`，其余金额逐项符合固定预期。 |
| 2. 半分舍入 | API 和自动测试执行小额样例，税额 `0.01`、应付 `0.11`；不能使用二进制浮点或银行家舍入替代。 |
| 3. 数量负向 | 参数化测试数量 `0`、`-1`、`true`，各自返回 4xx 和数量字段错误，无有效报价或文档被覆盖。 |
| 4. 金额/比率负向 | 单价 `"NaN"`、`"Infinity"`、`"1.005"`、负运费，以及税率 `"1.01"` 分别被拒绝；记录实际响应，不只断言抛异常。 |
| 5. 原始 Word | 生成并在 Word/Writer 实际打开原件；`inspect_file` 回读 `.docx`，核对中文、全部金额、日期、唯一标记，记录原件哈希。 |
| 6. GUI 修改 | 在修改稿 GUI 中改日期并保存；`inspect_file` 确认新日期，含税应付仍为 `391.51`、标记不变；原件哈希不变。 |
| 7. 选中复制粘贴 | 保存 Word 选区截图、clipboard 内容和真实 `ctrl+c/ctrl+v` 调用；`inspect_file` 分别回读修改稿和 `review.txt`，完整摘录一致，仅统一 CRLF/LF 和末尾换行，不宽松忽略正文字符。 |
| 8. 正向审阅 | 程序比较原件、修改稿与复制文字，写 `review-diff.json`：唯一业务改动为日期 `2026-11-06→2026-11-09`；金额差异为空、标记相同、复制段落一致。依据实际回读报告差异。 |
| 9. 审阅负向 | 仅在独立 `review-bad.txt` 测试副本将应付改为 `391.52`，实际运行同一审阅程序，必须报出金额差 `0.01` 并返回失败状态/非零退出码。保留正确的修改稿和 `review.txt`；拒绝该负向输入才算本用例通过。 |

## 证据与收尾

每关立刻保存 `uploads/windows-business-<run_id>-<gate>-evidence.json`：目标、端口、命令/工具、原始响应、真实 HTTP 状态或原生退出码、断言、现存截图/下载副本的完整路径及实际 SHA-256。敏感信息脱敏；不要等上下文裁剪后重建证据，模型总结或 JSON 内的 `passed` 不代替执行结果。

自动测试保存完整输出与真实返回码；Bash 命令后使用 `rc=$?; echo "TEST_EXIT=$rc"; exit "$rc"`，再核对上层进程退出码。负向用例分别记录“预期拒绝”和“实际拒绝”，不能把预期失败算成业务通过，也不能隐藏非预期失败。

最终按已执行、失败、未执行或待补验汇报；缺少 Word/Writer 或 GUI/回读证据时不宣称整链路完成。保留业务代码、数据、Word 原件/修改稿、审阅文件和运行环境。清理只处理有本轮创建记录的临时文件，逐项记录真实操作，未做写未执行。
